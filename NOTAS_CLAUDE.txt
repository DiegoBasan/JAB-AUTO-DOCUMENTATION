1. QUÉ ES ESTE REPO
-----------------------------------------------------------------------------
Herramientas HTML autocontenidas (sin servidor, sin build) que generan
documentos corporativos reales (Excel/PowerPoint) a partir de una plantilla
embebida en base64 + JSZip, manipulando el .xlsx/.pptx como zip+XML crudo,
sin tocar fórmulas/formato del original. El usuario describe una situación
en lenguaje natural, la IA (Gemini, vía API key del usuario) estructura los
datos, se validan/editan en la UI, y se genera el archivo final.

Herramientas en programas/:
- A3_Generador.html
- MRA_Generador.html   (Machine Risk Assessment)
- PPT_Generador.html
- RA_Generador.html    (Análisis de Riesgo / JSA)

Plantillas originales en plantillas/.

4. CÓMO GENERAR UN MRA (paso a paso probado y validado)
-----------------------------------------------------------------------------
NO usar el flujo de IA/Gemini del programa (no hay API key confiable en este
entorno). En vez de eso, usar Playwright para inyectar los datos
directamente en el modelo JS de la página (bypass de la UI):

1. Leer MRA_Generador.html y extraer los arrays de opciones válidas
   (cambian poco pero SIEMPRE verificar antes de usar, no asumir de memoria):
   DPH, FE, LO, NP (para HRN), TAREA_OPTS, PELIGRO_OPTS, CONTROL_ENG_OPTS,
   CONTROL_PROC_OPTS, ISO_SKILL, ISO_SPEED, ISO_AVOID, ISO_RECOG, ISO_COMPLEX.
   Estas están hardcodeadas en el HTML (no se leen del Excel en vivo).

2. Construir un array de objetos "riesgo" con esta forma exacta:
   {
     tarea, peligro,                       // strings EXACTOS de TAREA_OPTS/PELIGRO_OPTS
     personas:{operador,mantenimiento,contratistas,otros}, // booleans
     controlProc, controlEng,              // strings EXACTOS de las listas de control
     stage1:{dph,fe,lo,np},                // evaluación SIN salvaguardas
     stage4:{dph,fe,lo,np},                // evaluación residual CON controles
     iso:{skill,speed,avoid,recog,complex},// ISO 13849-1:2023
   }
   NO llenar fotoRiesgo/fotoMitigacion si el usuario va a poner las fotos él
   mismo (deja esos slots vacíos a propósito, el warning de "falta foto" es
   esperado y no es error).

3. Script Playwright (ver ejemplo real en git log, archivos
   fill_mra.js / fill_mra_gecko.js que ya NO existen en /tmp pero el patrón
   es reproducible):
   - page.goto('file:///.../programas/MRA_Generador.html')
   - fill #hCliente, #hUbicacion, #hResponsable, #hCelula
   - page.evaluate((riskData) => { riskData.forEach(rd => { const base =
     newRisk(); Object.assign(base, rd); risks.push(base); }); renderRisks();
     }, risks)
   - click #btnGenerar, esperar evento 'download', copiar a archivo.

4. VALIDAR SIEMPRE el .xlsx resultante antes de entregar (patrón repetido
   en toda la sesión, usar python3):
   - zipfile.testzip() -> None
   - lxml.etree.fromstring en cada .xml/.rels -> sin excepción
   - buscar r:id / r:embed colgantes contra cada _rels correspondiente
   - [Content_Types].xml: sin Overrides duplicados ni huérfanos (parte no
     existe en el zip)
   - openpyxl.load_workbook + inspeccionar celdas de las filas escritas

6. CÓMO GENERAR UN RA (distinto de MRA: catálogo se lee EN VIVO del Excel)
-----------------------------------------------------------------------------
RA_Generador.html NO tiene las opciones hardcodeadas: las lee en tiempo real
del workbook embebido (sharedStrings/definedNames/grids) via funciones
async ya definidas en la página:
  getRiesgosForCategoria(categoria)
  getConsecuenciasForRiesgo(riesgo)
  getControlesForRiesgo(riesgo)
  getEPPForRiesgo(riesgo)
  LISTS.categorias, LISTS.condicion, LISTS.controlInfluencia (ya cargadas)

IMPORTANTE: nunca asumir de memoria los strings de riesgo/consecuencia/
control -- SIEMPRE inspeccionar primero con un script Playwright que
llame a esas funciones y haga console.log(JSON.stringify(...)) antes de
armar los datos finales. Las categorías reales (confirmadas, sin acentos
raros) son:
  'Actividades de trabajo', 'Ergonomía', 'Eléctrico', 'Herramientas',
  'Lugar de trabajo', 'Mecanico' (SIN acento, ojo), 'Psicosocial',
  'Químicos', 'Seguridad'
condicion: 'Rutinario', 'No rutinario', 'Emergencia ' (con espacio al final),
  'Psicosocial'
controlInfluencia: 'Control', 'Influencia'

Riesgo -> función blankRisk() shape:
  { id, condicion, tarea, pasos, categoria, riesgo, consecuencia,
    controlInfluencia, severidad, probabilidad, control, epp, documento,
    ehs, nivelControl, _riesgoOpts, _consecuenciaOpts, _controlOpts,
    _eppSugerido }
Se agrega con addRiskCard(prefill) -> hace Object.assign(blankRisk(), prefill)
y pushea a risks[], luego renderRisks().

nivelControl: '1'=Eliminación(~100% reduce), '2'=Sustitución(~95%),
  '3'=Ingeniería(~85%), '4'=Administrativo(~15%), '5'=EPP(~0%)
RI = severidad(1-5) * probabilidad(1-5); RR = RI * factor de nivelControl.

Patrón de script Playwright para RA (reproducible):
1. Inspeccionar LISTS.categorias y, para cada categoría candidata, sus
   riesgos con getRiesgosForCategoria (script "inspect" aparte, SOLO
   lectura, antes de decidir los datos finales).
2. Para cada riesgo elegido, inspeccionar sus consecuencias/controles/epp
   reales con getConsecuenciasForRiesgo/getControlesForRiesgo/
   getEPPForRiesgo.
3. Armar el array final de riesgos con valores LITERALES ya confirmados
   (nunca fuzzyPick a ciegas -- fuzzyPick(list, guess) existe en la página
   pero es mejor usarlo solo como respaldo; preferir strings exactos
   validados en el paso 1-2, y en el propio script de inyección validar con
   throw si algo no está en la lista real antes de addRiskCard).
4. page.fill('#hProceso', ...), luego page.evaluate inyectando con
   addRiskCard(prefill) para cada riesgo (igual patrón que MRA).
5. click #btnGenerar, esperar 'download', copiar archivo.
6. Validar igual que MRA (zip/xml/Content_Types + openpyxl, hoja "RA Form",
   columnas A-N empezando en fila 8).

10. FAMILIA DE MÁQUINAS: KASALIS PIXID 500 (embotellamiento compartido)
-----------------------------------------------------------------------------
Máquina única (no una familia de estaciones repetidas como A/B) compartida
por TODAS las líneas de producción: SCORPION (4 variantes de FOV: 76°,
95°, 131°/135°, 133.4°), MOOSE, GECKO, INFURROW. Cualquier falla de esta
máquina detiene TODAS las líneas -- es el cuello de botella crítico de la
planta. La mecánica/electrónica NO cambia entre modelos, solo cambian
parámetros de visión (VIS) y offsets de dispensado (y a veces altura del
dispensador o plato de la torna-mesa).

Componentes:
- Torna-mesa con motor grande, 4 estaciones, cada una con su propio pistón
  neumático de clampeo.
- Mini-gantry 1 (dispensado): 3 ejes, sensores de límite y drivers propios;
  tooling = dispensador ViscoTech ECO-PEN450 (empuje neumático de adhesivo
  DELO) + cilindro de clampeo propio.
- Mini-gantry 2 (PnP): 3 ejes, sensores de límite y drivers propios;
  tooling = gripper + cilindro de clampeo propio.
- Sistema óptico: pogo de contacto (inspección MTF), eje Z con
  retroalimentación de enfoque (motor a pasos), fuente/LED UV para curado
  de DELO.
- Seguridad: cortinas de seguridad, interlocks en puertas de acceso,
  switch de llave Auto/Mantenimiento, E-stop, switch general LOTO Y
  (a diferencia de GECKO) SÍ tiene válvula de bloqueo/sangrado LOTO
  neumática instalada -- riesgo neumático residual bajo y bien controlado.
- Punto de MAYOR RIESGO (confirmado por el usuario): el operador tiene
  contacto DIRECTO con una de las 4 estaciones al cargar la pieza
  manualmente -- al colocarla se activa el cilindro de clampeo de esa
  estación. En el MRA se modeló con controlEng "Control de acceso:
  controles a dos manos" (en RA, el catálogo no tiene esa opción exacta,
  se usó "sensores" como aproximación y se documentó la discrepancia en el
  campo EPP/notas).

MRA/RA generados: documentos_terminados/MRA_Kasalis.xlsx y RA_Kasalis.xlsx
(9 riesgos cada uno, mismo orden): 1-torna-mesa, 2-gantry dispensador,
3-gantry PnP, 4-pistón de clampeo en estación de carga (mayor riesgo),
5-exposición química DELO, 6-arranque inesperado en mantenimiento,
7-energía neumática residual (SÍ tiene válvula, control "Válvulas de
alivio"/"Aislamiento neumático: válvula de seguridad; Bloquear/sangrado"),
8-eléctrico, 9-ergonomía.

Manual de proveedor: documentos_terminados/Manual_Kasalis_ITO.docx.
Sin fotos (el usuario no subió imágenes de esta máquina, solo dio texto),
así que el manual quedó basado en tablas/texto únicamente (portada y
header/footer sí llevan los logos ITO/Jabil). Incluye, además de las
secciones estándar (specs, descripción, seguridad, operación):
- Sección 6 "Cambio de Modelo": subir dispensador para MOOSE, cambio de
  cartucho DELO (purgar burbujas), cambio de modelo general (parámetros
  VIS + offsets ARC X=9.2/Y=6.4), cambio de plato, nota de que "cómo abrir
  cada modelo" varía por unidad física de Kasalis (no hay detalle
  suficiente para documentarlo genérico, se dejó como referencia al SOP
  específico de Jabil).
- Sección 7 "Guía de Solución de Fallas", transcrita y organizada del
  texto crudo que dio el usuario, en 3 tablas: Dispensado (Fault 233
  discontinuo/desplazado, Fault 222 visión), Comunicación/Pogo (rebote
  rápido = falso contacto/pin atascado; rebote intermitente = interposer/
  pines sucios/pieza mal puesta), Alineación (teach de Z, bypass manual
  vía "rotary parking" + botón "align").
- Sección 8 "Notas de Confiabilidad y Mejora Continua": Fault 102 (IPC
  deadlock, sistemático, causa raíz desconocida, mitigación = timeout de
  gripper 5s + force open) y Fault 155 (drift post-UV por desgaste de jaw
  del gripper, 10-30% scrap), más lista larga de riesgos mecánicos/
  eléctricos a vigilar (backlash eje Z, desalineamiento XY gripper, DELO
  curado en lugares indebidos, sello de cilindro gripper, encoder Z sucio,
  falta de UPS/backup de PLC, brownouts de 24V, degradación fuente UV) y
  las 7 acciones de mitigación prioritarias que dio el usuario.
  IMPORTANTE: esta sección es de CONFIABILIDAD/CALIDAD, no de seguridad a
  personas -- por eso NO se incluyó en el MRA/RA (que son de riesgo físico
  a personas). Si en el futuro se pide un FMEA o plan de mantenimiento
  predictivo formal para Kasalis, esta sección 8 del manual es la base
  lista para reutilizar.

YA RESUELTO -- Declaración de Seguridad (Machine Safety Statement) x7:
La plantilla real (plantillas/16-HS00-8018-00485-A DELCARACION DE
SEGUIRDAD.xlsx, hoja "Formato Template") NO es cell-based en su encabezado
-- es texto dentro de FORMAS/TEXTBOXES en xl/drawings/drawing2.xml (no
drawing1/3, esos son de las hojas "Ejem de llenado..." que hay que dejar
intactas). Solución que funcionó (ver build_declaraciones.py en el
historial de esta sesión):
1. Con zipfile, leer xl/drawings/drawing2.xml como texto y usar
   re.finditer(r'<a:t>([^<]*)</a:t>', xml) para obtener TODOS los runs de
   texto en orden. Los índices 31-49 (0-indexed) son el bloque de
   identificación: 31=MAQUINA/ID, 32=FECHA, 33-34=RESPONSABLE (2 runs),
   38=FECHA LIBERACION/BUY-OFF, 39-45=MOC/PLCM/UBICACION (varios runs,
   45=UBICACION), 46=No Doc de PLACARD, 47-49=VALIDADO EHS (3 runs).
   Reemplazar SOLO esos índices por posición (nunca por texto exacto --
   varios patrones tipo "_______" se repiten muchas veces en el resto del
   documento para otras secciones no relacionadas). Escapar '&','<','>'
   con xml.sax.saxutils.escape. Reempaquetar el zip reemplazando
   únicamente esa entrada, todo lo demás byte-a-byte igual (nunca tocar
   drawing1.xml/drawing3.xml).
2. La tabla "Energía / Pasos de bloqueo y prueba / EPP" SÍ es cell-based
   (fila 90 headers, filas 91-98 datos) pero el mapeo real NO es "un
   bloque de 8 pasos por cada energía" como parecía a primera vista:
   - F91 = label fijo "principal" (no tocar) -> F92 = VALOR de la energía
     principal (ej. "Eléctrica").
   - F94/F95 = label fijo "Energías "/"secundarias" (no tocar, 2 líneas)
     -> F96 = VALOR de la energía secundaria si existe (ej. "Neumática"
     para Kasalis); si no hay secundaria, dejar el "_____" original del
     template tal cual (NO sobreescribir).
   - Columna I (9), filas 91-98 = los 8 PASOS del procedimiento LOTO,
     compartidos/genéricos para todas las energías de esa estación (no se
     repite el bloque por energía, es una sola lista de 8 pasos).
   - Columna P (16) = EPP, unas pocas filas (91,93,95 aprox.).
3. No existe ningún <xdr:pic> real como placeholder de "foto del equipo"
   en la plantilla (los 7 <xdr:pic> que trae son iconos decorativos
   genéricos -- triángulo de advertencia, palomita, etc. -- NO fotos de
   máquina). Insertar una foto ahí vía las formas agrupadas del drawing
   complejo (96 anchors, grupos anidados con offsets) es alto riesgo de
   corromper el archivo. Solución usada: NO tocar el drawing complejo para
   la foto -- en su lugar, con openpyxl (segunda pasada, abriendo el xlsx
   ya parcheado) hacer un ws.add_image() simple anclado en una celda libre
   cercana (ej. B24) usando el sistema de anclaje normal de openpyxl, que
   es independiente del drawing2.xml de formas y no interfiere con él.
   Verificar con openpyxl.load_workbook(...)._images que el conteo sea
   +1 respecto al original tras esto.
