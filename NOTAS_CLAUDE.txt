1. QUÉ ES ESTE REPO
-----------------------------------------------------------------------------
Herramientas HTML autocontenidas (sin servidor, sin build) que generan
documentos corporativos reales (Excel/PowerPoint) a partir de una plantilla
embebida en base64 + JSZip, manipulando el .xlsx/.pptx como zip+XML crudo,
sin tocar fórmulas/formato del original. El usuario describe una situación
en lenguaje natural, la IA (Gemini, vía API key del usuario) estructura los
datos, se validan/editan en la UI, y se genera el archivo final.

Herramientas en programas/:
- A3_Generador.html
- MRA_Generador.html   (Machine Risk Assessment)
- PPT_Generador.html
- RA_Generador.html    (Análisis de Riesgo / JSA)

Plantillas originales en plantillas/.

4. CÓMO GENERAR UN MRA (paso a paso probado y validado)
-----------------------------------------------------------------------------
NO usar el flujo de IA/Gemini del programa (no hay API key confiable en este
entorno). En vez de eso, usar Playwright para inyectar los datos
directamente en el modelo JS de la página (bypass de la UI):

1. Leer MRA_Generador.html y extraer los arrays de opciones válidas
   (cambian poco pero SIEMPRE verificar antes de usar, no asumir de memoria):
   DPH, FE, LO, NP (para HRN), TAREA_OPTS, PELIGRO_OPTS, CONTROL_ENG_OPTS,
   CONTROL_PROC_OPTS, ISO_SKILL, ISO_SPEED, ISO_AVOID, ISO_RECOG, ISO_COMPLEX.
   Estas están hardcodeadas en el HTML (no se leen del Excel en vivo).

2. Construir un array de objetos "riesgo" con esta forma exacta:
   {
     tarea, peligro,                       // strings EXACTOS de TAREA_OPTS/PELIGRO_OPTS
     personas:{operador,mantenimiento,contratistas,otros}, // booleans
     controlProc, controlEng,              // strings EXACTOS de las listas de control
     stage1:{dph,fe,lo,np},                // evaluación SIN salvaguardas
     stage4:{dph,fe,lo,np},                // evaluación residual CON controles
     iso:{skill,speed,avoid,recog,complex},// ISO 13849-1:2023
   }
   NO llenar fotoRiesgo/fotoMitigacion si el usuario va a poner las fotos él
   mismo (deja esos slots vacíos a propósito, el warning de "falta foto" es
   esperado y no es error).

3. Script Playwright (ver ejemplo real en git log, archivos
   fill_mra.js / fill_mra_gecko.js que ya NO existen en /tmp pero el patrón
   es reproducible):
   - page.goto('file:///.../programas/MRA_Generador.html')
   - fill #hCliente, #hUbicacion, #hResponsable, #hCelula
   - page.evaluate((riskData) => { riskData.forEach(rd => { const base =
     newRisk(); Object.assign(base, rd); risks.push(base); }); renderRisks();
     }, risks)
   - click #btnGenerar, esperar evento 'download', copiar a archivo.

4. VALIDAR SIEMPRE el .xlsx resultante antes de entregar (patrón repetido
   en toda la sesión, usar python3):
   - zipfile.testzip() -> None
   - lxml.etree.fromstring en cada .xml/.rels -> sin excepción
   - buscar r:id / r:embed colgantes contra cada _rels correspondiente

     existe en el zip)

6. CÓMO GENERAR UN RA (distinto de MRA: catálogo se lee EN VIVO del Excel)
-----------------------------------------------------------------------------
RA_Generador.html NO tiene las opciones hardcodeadas: las lee en tiempo real
del workbook embebido (sharedStrings/definedNames/grids) via funciones
async ya definidas en la página:
  getRiesgosForCategoria(categoria)
  getConsecuenciasForRiesgo(riesgo)
  getControlesForRiesgo(riesgo)
  getEPPForRiesgo(riesgo)
  LISTS.categorias, LISTS.condicion, LISTS.controlInfluencia (ya cargadas)

IMPORTANTE: nunca asumir de memoria los strings de riesgo/consecuencia/
control -- SIEMPRE inspeccionar primero con un script Playwright que
llame a esas funciones y haga console.log(JSON.stringify(...)) antes de
armar los datos finales. Las categorías reales (confirmadas, sin acentos
raros) son:
  'Actividades de trabajo', 'Ergonomía', 'Eléctrico', 'Herramientas',
  'Lugar de trabajo', 'Mecanico' (SIN acento, ojo), 'Psicosocial',
  'Químicos', 'Seguridad'
condicion: 'Rutinario', 'No rutinario', 'Emergencia ' (con espacio al final),
  'Psicosocial'
controlInfluencia: 'Control', 'Influencia'

Riesgo -> función blankRisk() shape:
  { id, condicion, tarea, pasos, categoria, riesgo, consecuencia,
    controlInfluencia, severidad, probabilidad, control, epp, documento,
    ehs, nivelControl, _riesgoOpts, _consecuenciaOpts, _controlOpts,
    _eppSugerido }
Se agrega con addRiskCard(prefill) -> hace Object.assign(blankRisk(), prefill)
y pushea a risks[], luego renderRisks().

nivelControl: '1'=Eliminación(~100% reduce), '2'=Sustitución(~95%),
  '3'=Ingeniería(~85%), '4'=Administrativo(~15%), '5'=EPP(~0%)
RI = severidad(1-5) * probabilidad(1-5); RR = RI * factor de nivelControl.

Patrón de script Playwright para RA (reproducible):
1. Inspeccionar LISTS.categorias y, para cada categoría candidata, sus
   riesgos con getRiesgosForCategoria (script "inspect" aparte, SOLO
   lectura, antes de decidir los datos finales).
2. Para cada riesgo elegido, inspeccionar sus consecuencias/controles/epp
   reales con getConsecuenciasForRiesgo/getControlesForRiesgo/
   getEPPForRiesgo.
3. Armar el array final de riesgos con valores LITERALES ya confirmados
   (nunca fuzzyPick a ciegas -- fuzzyPick(list, guess) existe en la página
   pero es mejor usarlo solo como respaldo; preferir strings exactos
   validados en el paso 1-2, y en el propio script de inyección validar con
   throw si algo no está en la lista real antes de addRiskCard).
4. page.fill('#hProceso', ...), luego page.evaluate inyectando con
   addRiskCard(prefill) para cada riesgo (igual patrón que MRA).
5. click #btnGenerar, esperar 'download', copiar archivo.
6. Validar igual que MRA (zip/xml/Content_Types + openpyxl, hoja "RA Form",
   columnas A-N empezando en fila 8).

  - El paquete 'docx' NO viene preinstalado en este entorno pese a lo que
    dice el skill -- hay que hacer `npm install docx` en la carpeta de
    trabajo (scratchpad) antes de `require('docx')`.
  - Archivo de trabajo usado: scratchpad/manual_sttor/build.js (borrador
    completo reproducible, ver historial de conversación para el código).
  - Bug real encontrado y corregido: usar ImageRun con `type:'png'` para un
    archivo que en realidad es .jpg (o viceversa) NO truena en python-docx/
    lxml (no validan bytes vs tipo declarado), pero SÍ puede causar que
    LibreOffice rechace cargar el archivo completo. Verificar SIEMPRE que
    el `type` de cada ImageRun coincida con el byte-signature real
    (JPEG=ffd8ff.., PNG=89504e47) antes de dar por bueno un docx con fotos
    mixtas jpg/png.
  - Entorno con LIMITACIÓN CONOCIDA: `soffice --headless --convert-to pdf`
    FALLA en este entorno incluso con un .txt trivial ("Error: source file
    could not be loaded"), confirmado que es un problema del entorno/
    sandbox de LibreOffice, NO del docx generado. No perder tiempo
    debuggeando esto de nuevo -- ya se probó: LD_PRELOAD shim, distintos
    UserInstallation profiles, strace (no mostró error real, el binario
    soffice.bin simplemente falla). Si se necesita preview visual, avisar
    al usuario que no se pudo renderizar en este entorno y validar solo
    con python-docx + lxml + revisión de bytes de imágenes.
